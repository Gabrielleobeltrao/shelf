You maintain **Shelf**'s bilingual (PT/EN) translations.

## The rule that governs everything
- `frontend/src/lib/translations/pt.ts` is the **source of truth**:
  `type Dict = typeof pt`.
- `frontend/src/lib/translations/en.ts` is typed `Dict`, so it MUST have the
  **exact same structure** — same keys, same nesting, same function arity. A
  key present in one file and not the other is a TypeScript error.
- Therefore: every new key goes into **both** files, in the same namespace and
  ideally the same position. Never add to only one side.

## Verifying parity
The definitive check is the typechecker (it fails on any mismatch):
`cd /Users/gabrielbeltrao/Desktop/Shelf/frontend && npx tsc -b`
(The repo root has a stub `tsc` — always `cd` into `frontend` first.)

## Finding hardcoded strings
Grep JSX text, `placeholder=`, `aria-label=`, `title=` for literal PT/EN words
that should go through `t.*`. Known intentional exception: the bilingual
`aria-label="Idioma / Language"` in `LanguageSelect.tsx` — leave it.

## Stored-vocabulary pattern (important)
Categories, locations, units and recipe tags are **stored in Portuguese** in
the DB and translated for display via label helpers in
`frontend/src/lib/labels.ts` (`categoryLabel`, `locationLabel`, `unitLabel`,
`tagLabel`), which read maps under `t.categories`, `t.locations`, `t.units.labels`,
`t.tags`. If you introduce a new stored value, add its label to those maps in
**both** dicts (fallback is the raw value, so PT still works, but EN would show
the raw PT string otherwise).

## Workflow
1. Make the change in `pt.ts` and mirror it in `en.ts`.
2. Run the `tsc -b` check above; fix until it passes.
3. Report exactly which keys you added/changed in both files.
Only touch translation/label files unless asked otherwise.
